# Release Notes: v1.2.0

## Focus

`v1.2.0` is the current Workbench package release line for the local Docker
launcher experience. It publishes a GitHub Release asset set that matches the
supported ZIP install path in `README.md` and `INSTALL.md`.

This release remains local-first and single-user. Its release evidence proves
the supported local/self-hosted Workbench path; it is not public/shared
deployment certification.

## Highlights

- Ships the current local Workbench source tree for the FastAPI backend,
  workflow worker, React frontend, Docker Compose runtime, and OS launchers.
- Adds the end-user Workbench release ZIP as a first-class GitHub Release
  asset, built from the exact tagged tree with `make release-bundle`.
- Includes `BUNDLE-MANIFEST.json` inside the ZIP with per-file SHA-256 values,
  plus release-level checksum files for the generated artifacts.
- Keeps the backend distribution name aligned with the current package:
  `vuln-prioritizer-workbench`.
- Uses draft-first GitHub Release publication so maintainers can verify assets,
  checksums, release notes, and evidence before publishing the release.

## Release Assets

The GitHub Release for `v1.2.0` should contain:

- `vuln_prioritizer_workbench-1.2.0-py3-none-any.whl`
- `vuln_prioritizer_workbench-1.2.0.tar.gz`
- `vuln-prioritizer-workbench-local-1.2.0.zip`
- `vuln-prioritizer-workbench-local-1.2.0-manifest.json`
- `vuln-prioritizer-workbench-local-1.2.0.zip.sha256`
- `dist-sha256.txt`

The release ZIP contains the local Workbench launchers, Compose files, backend,
frontend, docs, demo data, and `BUNDLE-MANIFEST.json`. It excludes local build
outputs, virtual environments, databases, generated reports, uploads,
diagnostics, provider caches, and dependency directories.

## Validation

Release-prep validation:

```bash
python3 -m pytest -q backend/tests/test_release_bundle_script.py --no-cov
make package-check
make release-bundle
make docs-check
make workflow-check
```

The tag workflow must run `make release-readiness-check` before the draft GitHub
Release is created. The release owner should link the workflow run and
`release-readiness-evidence` artifact from the release issue or release notes
handoff.

## Notes

- Do not attach new `v1.2.0` ZIP assets to the old `v1.1.0` release.
- Public PyPI publication remains gated by repository configuration and is not
  required for the GitHub Release ZIP deliverable.
- Public or shared deployment readiness requires separate candidate-specific
  evidence from the public deployment runbook and release evidence ledger.
