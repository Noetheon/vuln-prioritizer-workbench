# Release Notes: v1.3.0

## Focus

`v1.3.0` makes the local single-process Workbench the standard installation
path. The packaged `vpw serve` command runs the FastAPI API, same-origin
frontend, supervised Workflow v2 worker, migrations, and local SQLite state
without requiring Docker for a new installation.

This remains a local-first, single-user Beta release. It does not certify a
shared or public deployment, add browser authentication or RBAC, or turn VPW
into a scanner, exploitation tool, or automated patcher.

## Highlights

- Adds the immutable Decision Ledger: per-run decision history stays append-only
  while indexed current projections serve filtering, sorting, dashboards, and
  lifecycle updates.
- Ships `vpw serve`, Decision Ledger maintenance, and explicit migration
  commands in the built wheel together with the frontend, Alembic revisions,
  and offline demo resources.
- Adds verified PostgreSQL-to-SQLite migration with schema-head checks, exact
  row digests, complete Ledger parity, artifact hash verification, foreign-key
  validation, safe path relocation, and atomic target activation.
- Hardens SQLite backup and restore around WAL state, integrity checks, archive
  validation, active-sidecar refusal, and atomic replacement.
- Keeps Docker Compose/PostgreSQL as a deprecated compatibility path for one
  transition release; existing data is never migrated implicitly.
- Refreshes Python and frontend dependency locks, generated API bindings, and
  the backend runtime image to pinned Python 3.13.14.

## Migration Evidence

The release candidate was rehearsed against an anonymized copy of an existing
Workbench database, not only synthetic fixtures. The rehearsal upgraded the
source schema, preserved all 24 Decision Ledger rows, loaded 28 application
tables and 245 rows into PostgreSQL, restored a real `pg_dump` into a second
empty PostgreSQL database, and migrated that restored state into a fresh
SQLite runtime with exact table/digest parity. The packaged `vpw serve` runtime
then completed imports, all six report formats, a provider update, restart, and
state-persistence checks. Private source data and temporary rehearsal artifacts
were removed after verification.

## Release Assets

The draft GitHub Release for `v1.3.0` must contain:

- `vuln_prioritizer_workbench-1.3.0-py3-none-any.whl`
- `vuln_prioritizer_workbench-1.3.0.tar.gz`
- `vuln-prioritizer-workbench-local-1.3.0.zip`
- `vuln-prioritizer-workbench-local-1.3.0-manifest.json`
- `vuln-prioritizer-workbench-local-1.3.0.zip.sha256`
- `dist-sha256.txt`

The local ZIP retains the deprecated Compose compatibility files and launchers
for existing installations. New installations should use the wheel and
`vpw serve`.

## Validation

The exact release candidate must pass:

```bash
make package-check-temp
make release-readiness-check
make quality-10-check
```

The tag workflow reruns `make release-readiness-check`, builds and validates
the wheel, sdist, and local ZIP, tests both the built wheel and source-at-tag
install paths, records SHA-256 values, and creates the GitHub Release as a
draft. The draft must remain unpublished until its tag, notes, asset names,
hashes, ZIP manifest, and workflow evidence have been inspected.

## Known Boundaries

- Package-registry availability is separate live state; do not infer it from a
  GitHub tag or draft Release.
- Public/shared deployment readiness still requires candidate-specific proxy,
  TLS, authentication, retention, backup, and operational evidence.
- The stable runtime remains Python 3.13. Grype's only listed fix for
  `CVE-2026-15308` is Python 3.15.0, so the container policy keeps one exact
  package/version waiver that expires automatically when the runtime moves.
